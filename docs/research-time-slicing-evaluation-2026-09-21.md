# 研究工作区 1,000 个主动时间节点分片报告（2026-09-21）

## 结论

1,000 个同步 Clock 可以在真实 Edge 中持续运行，并按现有 `256` 个时间源 / `4 ms` 预算分成四个计算片段；同一仿真时刻的 1,000 个 Pulse 仍只作为一个完整确定性批次对外提交，没有暴露半完成状态。

首次浏览器基线同时暴露了计算分片之外的渲染瓶颈：每个批次完成后，画布同步刷新全部 1,000 个节点，导致帧间隔中位 82.9 ms、P95 100.2 ms。现已把连续仿真的投影展示改为合并更新，并限制为每帧最多 128 个节点、最多 4 ms；单步、复位、编辑和模型更新仍同步显示。复测帧间隔中位为 16.7 ms、P95 为 17 ms，V3 模型、事件语义、保存格式和渲染后端均未改变。

本报告不设置跨机器绝对性能门槛，也不宣称零卡顿。最终样本仍出现一次 55 ms Long Task 和 83.4 ms 最大帧间隔，但常态帧响应已不再被全量投影刷新持续占用；当前数据不支持引入 WebGL 或更换渲染后端。

## 环境与命令

- 系统：Windows 11 家庭版中文版 64 位，版本 10.0.26200。
- 处理器：Intel Core i9-13900HX，24 核 / 32 逻辑处理器；可见内存 47.7 GiB。
- 浏览器：Microsoft Edge 153.0.4234.48，Playwright 驱动。
- 视口：1,440 × 900，DPR 1，`prefers-reduced-motion: reduce`。
- 命令：`node tests/research-time-slicing-browser.js <本地 URL> [report.json]`。
- 数据边界：测试通过拦截 `/api/research/workspace` 提供一次性 V3 文档，不读取或写入真实 `data/research-workspace/`。

## 夹具与验收方式

夹具包含恰好 1,000 个周期为 16 ms 的 Clock，没有导线。所有节点在相同仿真时刻到期，因此每个边界都会同时产生 1,000 个 Pulse，刚好覆盖事件批次的安全上限，也迫使调度器遍历全部 1,000 个主动时间源。

浏览器验收覆盖：

- 加载后真实挂载 1,000 个 DOM 节点，且 V3 Schema、编译节点数和状态节点数均为 1,000。
- 以 4× 速度运行，读取最后一个 Clock 的公开结果；每次可见序号只能按 1,000 的整数倍推进。
- 捕获 `setTimeout(0)` 协作让出次数，验证每个完整批次至少有三次让出，对应四个不超过 256 个源的片段。
- 运行中调用公开工作区 `suspend()`，确认序号停止；再次 `activate()` 后继续运行。
- 使用公开“暂停”按钮停止，等待分片投影展示收尾后确认序号不再变化。
- 记录 RAF 帧间隔、Long Task、暂停响应、激活、三次冷重载、保存次数和文档大小。
- 确认调度计数、Pulse 数和仿真时间没有进入保存文档。

性能数字只报告，不作为易受机器影响的硬失败条件；完整批次、协作让出、暂停/恢复、Schema、无计算错误和非持久化属于功能断言。

## 前后对比

两次样本使用相同机器、Edge、视口、夹具与命令。基线是在确认计算已经分片、但投影仍同步全量刷新时测得；修正后样本包含新的逐帧投影分片。

| 项目 | 同步全量投影基线 | 合并并逐帧投影 |
| --- | ---: | ---: |
| RAF 帧间隔中位 | 82.9 ms | 16.7 ms |
| RAF 帧间隔 P95 | 100.2 ms | 17 ms |
| RAF 最大间隔 | 116.4 ms | 83.4 ms |
| Long Task | 2 次，共 117 ms，最大 61 ms | 1 次，共 55 ms |
| 公开暂停响应 | 98.5 ms | 90.6 ms |
| 三次冷重载中位 | 573 ms | 542 ms |

暂停响应改善有限，说明它不仅受节点投影刷新影响，也包含高频事件批次、浏览器输入任务排队和自动化派发时间。当前没有用该单项数字设门槛。

## 实现判断

- 计算调度器已有的时间源分片有效：部分片段期间 `simulationTime` 不前进，只有完整处理 1,000 个同刻源后才统一提交 Pulse。
- 主要持续卡顿来自展示层同步扫描并写入全部节点，而不是缺少计算分片。连续运行现在只排队一轮最新投影；已有展示任务不会因更高频的新批次反复从头开始。
- 每个展示帧只更新有限节点并直接刷新计算装饰，不重复写节点位置、标题等静态 DOM。单步与复位保持同步，避免用户操作后等待多帧才看到权威结果。
- 一次 55 ms Long Task 与 83.4 ms 最大帧间隔仍值得在未来复杂下游负载中观察，但本轮 P95 已回到显示刷新节奏，没有证据要求 WebGL、第二份渲染模型或持久结构变化。
