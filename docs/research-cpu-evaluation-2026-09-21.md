# 研究工作区分层 CPU 公开交互验收（2026-09-21）

## 结论

V3 子电路已经能只通过研究工作区公开 UI，从空白文档搭建、调试、修订并运行一个 4 位累加器 CPU。25 个 CPU Core r2 实例递归展开为 1,006 个叶节点和 1,356 根导线；最终快照通过 V3 Schema 与编译校验，没有组合环、类型错误、预算错误、控制台错误或页面异常。

本轮没有发现需要修改生产代码的正确性阻塞，也没有据此新增专用定义编辑器、批量模块操作、节点类型或渲染后端。下一项性能工作仍是 1,000 个主动时间节点的真实浏览器分片报告；本文的 1,006 个展开节点以组合逻辑为主，不能替代该验收。

## 电路与修订

CPU 使用 4 位 PC/ACC 和 8 位指令：`LDI`、`SUB`、`JNZ`、`HLT`。

| 模块 | 公开端口 | 实现说明 |
| --- | --- | --- |
| ROM | `pc: Bits<4> → instruction: Bits<8>` | r1 为 `03 11 21 F0`，r2 把首条指令改为 `05`。 |
| Decoder | `instruction → operand + isLdi/isSub/isJnz/isHalt` | Slice 与 Compare 组合。 |
| ALU | `acc/operand/isLdi/isSub → nextAcc` | 4 位减法与 Select 组合。 |
| Control | `pc/acc/operand/isJnz/isHalt → nextPc` | 顺序取指、条件跳转和停止保持。 |
| CPU Core | `pcTick/accTick → pc/acc/instruction/halt` | 嵌套上述四个模块与两个 Register；两个 Pulse 输入如实反映事件端口目前不能在定义内部自动扇出。 |

先发布 ROM r1 与 CPU Core r1，再发布 ROM r2，并把使用 ROM r2 的嵌套 Core 发布为 r2。发布新修订后旧实例仍固定在 Core r1；兼容边界端口沿用稳定 ID。公开属性面板手动升级到 r2 后，PC/ACC 状态立即清零，随后执行 r2 程序。

## 功能结果

- r1 程序 `LDI 3 → SUB 1 → JNZ 1 → HLT` 在 8 次单步后稳定于 `PC=3、ACC=0、instruction=F0、HLT=true`。
- r2 程序 `LDI 5 → SUB 1 → JNZ 1 → HLT` 在 12 次单步后到达相同停止状态。
- Probe 记录了每次 Clock Pulse，并按真实顺序显示 r1 的 ACC `3→2→1→0` 和 r2 的 `5→4→3→2→1→0`；同一仿真时刻先记录 Pulse，再记录寄存器提交后的值变化。
- 25 个 Core r2 共用一个 Clock，经两个显式 Pulse 入口同步驱动 PC/ACC；五轮、每轮 12 步均得到相同结果。
- 三次冷重载后，定义修订、实例固定版本、导线和运行配置均保留；Probe 轨迹、事件队列与编译统计没有进入保存文档。

最终文档含 3 页、5 个定义、7 个修订，UTF-8 JSON 大小 67,804 字节；规模页有 31 个顶层节点、56 根顶层导线，展开后为 1,006 个节点、1,356 根导线和 51 个状态节点。

## 工作流观察

- 公开添加面板、双击放置、属性面板、端口拖线、多选封装、修订发布、实例升级、运行栏和 Probe 足以完成这台 CPU，没有必须绕过 UI 的步骤。
- 值端口跨子电路边界时，需要在定义中放置显式输入适配节点；事件入口无法在定义内部一对多扇出，因此 Core 暂时暴露 `pcTick` 和 `accTick` 两个 Pulse。这是现有语义的直接表达，不是测试夹具注入的捷径。
- Probe 已足以定位同步批次中的 Pulse 与 ACC 变化顺序。对本轮规模，调试能力没有成为阻塞。
- 主要摩擦是重复的节点配置、连线和边界端口命名，以及发布 ROM r2 时需要重新组合 Core r2。651 次公开操作说明专用定义编辑器或批量模块操作可能有价值，但本轮没有足够证据把它们提升为先决条件。
- 1,006 个递归展开节点的编译、执行和重载均完成；该结果只证明当前组合逻辑与 51 个状态节点的场景，不外推到 1,000 个同时活跃的 Clock/Timer 等时间节点。
