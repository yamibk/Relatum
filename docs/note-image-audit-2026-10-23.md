# 笔记图片与运行稳定性调查 · 2026-10-23

重点排查图片插入、剪贴板、拖放、异步选区交接、自动保存和图片测量，同时回归笔记输入、滚动、索引、搜索及图谱的既有边界。所有测试使用一次性笔记库和浏览器配置，没有打开或改写用户的 `notes/`、`data/`、画布或发布包。

## 已复现的问题

基线为 `9f9a80d`。同一真实本地 API 下由测试替换旧/新前端响应；延迟只加在测试网络响应上，不修改生产计时。

| 场景 | 基线行为 | 修复后的行为 |
| --- | --- | --- |
| 上传未完成时选中另一段正文 | 图片替换后来选中的文字，原文丢失 | 在初始位置插入，保留后来的选区与文字 |
| 上传时在初始位置之前输入 | 按完成时的光标插入，位置改变 | 临时范围随 CodeMirror 的真实变更映射 |
| 上传期间改写原待替换选区 | 迟到图片继续插入 | 取消插入，不覆盖新内容 |
| 切到其他笔记，再回到原路径 | 旧上传重新写入已重开的正文 | 核对文档身份及打开序号，拒绝旧结果 |
| 最小化后立即还原 | 旧响应仍可插入 | 可见生命周期变更后保持取消 |
| 同批导入 40 张图片 | 40 次正文变更 | 1 次正文变更；成功图片保持原顺序 |
| 超过 40MiB 的文件 | 先执行 FileReader/Base64 和 JSON，再由后端拒绝 | 读取前拒绝，零读取、零上传 |
| FileReader 被取消 | Promise 不结清，导入操作一直等待 | 正常进入失败收尾，下一次导入可继续 |
| 没有响应的图片请求 | 没有专项超时 | 45 秒取消请求并释放队列 |
| 图片状态不变的 100 次普通光标移动 | 100 次图片工具栏更新 | 0 次重复通知 |

超大文件的前端测试通过覆盖 `File.size` 验证读取顺序，不实际分配数百 MiB。取消和超时用测试替身确定性触发；旧的取消 Promise 不结清不等于已证明整页主线程死循环。批次更新次数是明确的工作量对照，不把单轮上传耗时当作可靠帧率或速度结论。

## 内存与计算边界

原上传只验证压缩文件字节数，尺寸很大的压缩图片可能以很小的文件触发大量解码内存。新增标准库文件头尺寸检查，覆盖 PNG、JPEG、GIF、BMP 和 WebP 的 VP8、VP8L、VP8X；不调用 Pillow 或其他图片解码器。已识别尺寸的单边限制为 32768，总像素限制为 67108864，适用于上传、导入及已有图片读取。大图拒绝发生在创建新附件或发送给浏览器之前，原文件与 Markdown 保留。

普通 PNG/GIF/BMP 读取检查只增加 32 字节的头读取。JPEG/WebP 需要时最多扫描 1MiB；这是有预算的风险控制，未知、损坏或元数据超过预算的头仍由原图片加载失败路径处理，不是完整格式验证。解码内存大小仍取决于浏览器、格式及同时可见的图片数量，不能承诺固定 RAM 降幅。

前端保留原 Base64 JSON 接口，读取和上传按批次串行，批量成功后只投影一次；没有增加后台循环。图片文字尺寸先集中读取再写入，重复尺寸不改样式，降低 ResizeObserver/编辑器测量之间的重复失效。图片状态相同不重复遍历和改写整组工具栏控件。

临时插入目标不保留全文字符串，只记录范围、路径和文档序号；完成、取消、文档替换或编辑器销毁时释放。不删除已写入的附件，以免损及共享引用。上传期间用户继续输入时，光标和选区依正常变更映射，不把它们强制恢复到旧状态。

宿主设置 `RELATUM_PLAYWRIGHT`、`RELATUM_EDGE_PATH` 和 `RELATUM_PYTHON`。新测试自身管理隔离服务和库；后端合集另外设置一次性 `RELATUM_DATA_ROOT` 后运行：

```powershell
node tests/note-image-upload-browser.js
node tests/note-image-text-browser.js
node tests/note-image-text-workspace-browser.js
node tests/note-image-copy-browser.js
node tests/note-input-browser.js
node tests/note-scroll-browser.js
powershell -File tests/run-note-checks.ps1 -Python <宿主Python路径>
```

图片导入回归覆盖空文档、行内、正文末尾、表格/代码之后、真实 Clipboard API + Ctrl+V、DataTransfer 粘贴/拖入、多图、迟到响应、部分失败、取消及超时后的恢复。计数探针只由测试注入。175 项后端与功能边界测试中 174 项通过，1 项因 Windows 符号链接权限跳过；11 项脚本回归包含 3556 次语法增量/完整重建对照。图片文字、图片复制/重贴、正文输入及滚动回归通过。

位置记忆与外部同步回归通过；搜索回归的完整、仅笔记及禁用内嵌画布三种模式通过。可见生命周期回归覆盖完整、禁用内嵌画布、禁用图谱和 Canvas2D 四种模式。并发运行验证时，禁用内嵌画布模式曾在还原后的链接刷新断言超时；同模式独立复测及随后完整四模式串行复跑均通过。该次超时原因尚未确认，保留此记录，没有将其宣称为已修复问题。

同一导入测试也在 `D:\Relatum-notes-performance-release-2026-10-22` 的真实 EXE/WebView2 中通过，测试仅将当前前端文件作为 HTTP 响应返回，服务和浏览器配置独立。这验证了真实桌面渲染器与剪贴板中的前端修改；该已有 EXE 的后端未被替换，新 Python 文件头检查另由源码后端测试验证。

## 尚未确认的范围

普通图片的连续粘贴、拖放和桌面测试没有稳定复现“所有按键都失效、必须由任务管理器结束”的整页卡死，因此不能把这次风险控制和异步错误修复称为已根除该现象。没有在浏览器里主动解码会占用 GiB 内存的测试图，也没有用户原始触发图片或崩溃转储。若同一图片在新包仍触发卡死，应依据该文件、尺寸、操作顺序及 WebView2 进程诊断继续定位。
