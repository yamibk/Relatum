# 笔记 SQLite 索引验收：2026-10-12

本次实现单库、可重建的 Markdown 派生索引、增量同步、删除清理及现有浏览界面的全文搜索。真实 Markdown、素材和本机配置未批量修改，演示目录未纳入提交。实现及接口见 [notes-sqlite-search.md](notes-sqlite-search.md)。

## 可复现方法

运行 Windows 11 26200、Intel i9-13900HX（24 核/32 线程）、约 47.7 GiB 内存；Python 3.12.14、SQLite 3.53.1。Edge 155.0.4283.45，WebView2 154.0.4258.62。原生桌面包由构建环境的 Python/SQLite 能力预检查后生成，发布目录和 WebView 配置均位于一次性 TEMP 路径。

```powershell
python tests/note-index-performance.py --counts 2000 10000 50000 --layouts mixed flat --output report.json
```

夹具是真实 UTF-8 Markdown：每篇 8 个双链、正文、代码、分层标签、中英文和 emoji；每 1000 篇另有约 9 万字符长文。`mixed` 一半放默认本，其余分布在 5 个自定义本/20 个目录；`flat` 集中默认本根目录。另加保存用文档。所有源文件、索引及数据库均在新临时根内。

首次构建从后台激活计时，包含目录登记、正文派生和索引；重启核对文件状态并复用旧派生文本。每种热查询预热 1 次、测量 40 次；p95 用 nearest rank，无剔除慢样本。查询时将 `os.scandir` 与 Markdown 读取器替换为抛错探针，证明热查询不走全库文件扫描或未变正文重读。不是通过少量读取“估算为零”。

保存测量 60 次真实原子落盘，与同库后台未激活时基线比较；另删除含 1024 篇的笔记本，在清理期间测保存。每组还有 10 轮同路径创建/删除，每轮 20 篇，检查 UUID 不复用、逻辑删除即刻不可搜索、旧 GC 不影响新本、增量回收完成后空闲页为零和完整性 `ok`。p95 的百分比对约 1–3ms 基线非常敏感，不能据负值宣称后台构建让保存更快。

原始记录保留[第一轮](note-index-performance-2026-10-12.json)、[调度/清理改进后的六组复测](note-index-performance-followup-2026-10-12.json)及[目录通知收敛到受影响子树后的 1 万篇多本补验](note-index-performance-final-check-2026-10-12.json)。第一轮没有省略未达标组合，六组复测增加了清理中按前台状态停止后续工作、扫描批次让出执行，最后一次补验针对唯一仍波动的组合。草稿测量没有混入下表。

两种 5 万篇分布的目录/标签/反链 ≤50ms、常规全文 ≤150ms、宽泛短字符 ≤300ms 均满足。所有规模热查询零目录扫描、零 Markdown 正文读取，重启未变正文读取也为零。FTS5 与短字符项在同一事务发布。

索引第一次完整构建约 5 分钟，目录登记约 9–12 秒，完成前仍可使用已登记目录和已解析结果。这是实测开销，不是即时导入承诺。实际工作集在 5 万篇时约 116–135 MiB；同一测试进程累计峰值最高约 247 MiB。Windows 的峰值工作集是进程生命周期值，后续小规模样本不能当成该库独立峰值；JSON 保留了这一口径。索引体积受中文短字符项、派生文本、链接密度和长文比例影响，不把该夹具体积推广到所有笔记库。

六组复测的 5 组保存增幅满足 ≤20%，多本 1 万篇曾出现 1.501→2.092ms（+39.4%），原始数据保留。多本 5 万篇复测构建/清理 p95 为 1.988/1.796ms，单本 5 万篇为 1.968/1.858ms，两种分布的查询、保存、完整性和空间回收都通过本轮目标。

最后将普通目录通知限制到受影响子树，并补验 1 万篇多本：基线 p95 2.579ms，构建 1.509ms、清理 1.572ms，目录 p95 1.867ms、宽泛全文 29.908ms，保存目标通过。首次构建 64.4 秒，重启 580.6ms，10 轮同路径创建/删除及清理约 11.8 秒，索引完整性 `ok`、空闲页 0。**最终补验覆盖了此前未通过组合，但六组并非在同一轮全部通过；毫秒级保存百分比存在同机波动。** 这些负增幅不能解释为索引提高文件落盘速度，后续发布回归应继续记录绝对延迟和同轮基线。

## 搜索位置映射局部复核

`note_search.source_range()` 及 `hit()` 的原始显示还原原先从第一个位置段扫描；现在按有序段末端二分定位，只遍历命中附近区间。派生格式和查询结果不变。与 `ffb7de4` 在同一进程、同一临时 SQLite 库中比较，预热一次后各测 11 次，以下为中位数（毫秒）。

| 合成场景 | 原实现 | 优化后 |
| --- | ---: | ---: |
| 50 次长笔记文末结果生成，映射已解码 | 212.679 | .448 |
| SQLite 完整查询，10 篇长笔记均在文末命中 | 348.699 | 305.728 |
| 50 次短笔记结果生成 | .392 | .567 |

长文夹具为 `**Heading** cafe\u0301 Straße English 😀\n`（实际使用组合字符和换行）重复 6000 次，末尾追加 `最后 needle 匹配\n`，UTF-8 240021 字节、48000 个位置段和30000 个显示段。查询夹具直接以生产投影及索引写入器登记 10 篇相同正文，单次查询包含 SQL 排序、映射解压/JSON 解码及摘要生成；结果逐项与旧实现一致。短文仅重复一次，61 字节，每条结果增加约 .0035ms。这是映射密集、靠后命中的专项收益，不能推为所有搜索或工作区整体提速；映射解码仍是长文查询的主要剩余成本，本次不扩大缓存或改派生结构。

验证：索引、API、浏览及笔记库共 85 项，84 通过、1 项平台场景跳过；另有 10000 组位置边界与旧实现对照通过。`node tests/note-search-browser.js full` 的实际 Edge 搜索、分页、图片文字、emoji/长文定位和编辑/阅读跳转通过。新增回归检查位置段边界/空隙，以及长文尾部定位不遍历全部映射；所有夹具和数据库均隔离。
